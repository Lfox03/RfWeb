# AGENTS.md

RFID attendance system (French UI): npm-workspaces monorepo — TypeScript server (`server/`, Express 5 + better-sqlite3 + node-hid + ws) and React dashboard (`client/`, Vite 8 + React 19 + react-router-dom 7). Phases 1–12 done: DB migrations layer, cookie auth + user management, kiosk mode, multi-group sessions, auto-scheduler, reporting + CSV export, student CSV import, sortable tables. The legacy JS prototype is **deleted**; only `rfid/rfidApi.js` + `rfid/rfidWorker.js` remain as the hardware layer, reached exclusively through the `RfidReader` interface (`server/src/rfid/reader.ts`, lazy-required).

## Commands (always from the repo root)

- `npm install` — native modules (`better-sqlite3`, `node-hid`) and `esbuild` need install scripts: approve them if binaries are missing (`npm install-scripts approve better-sqlite3` …). Node >= 20.12.
- `npm run dev` — server (`tsx watch`, `HTTP_PORT`) + Vite 5173. Vite proxies **both** `/api` and `/ws` → `http://127.0.0.1:3000` (the WS hub is mounted at `/ws` on the HTTP port in dev AND prod — `WS_PORT`/8080 is never used by the client). Client code uses **relative URLs only** (`fetch("/api/…")`, WS URL built from `location`) — never hardcoded localhost.
- `npm run build` — server first (`tsc` → `dist/server/`), then client (`vite` → `client/dist/`). `npm start` = `node dist/server/index.js` (serves `client/dist/` + SPA fallback).
- `npm run typecheck` — **server only**; the client is typechecked by its `tsc` inside `npm run build`.
- `npm run db:migrate` · `db:seed` · `db:verify` (97 checks) · `api:verify` (508 checks).
- Migrations run automatically at every server boot. Seed NEVER runs at boot (demo cards 9000001/9000002 are skipped if those UIDs are already assigned; admin password = `SEED_ADMIN_PASSWORD`, default `admin`).
- `api:verify` (`server/src/dev/verifyApi.ts`) is the repo's test suite (no framework): fresh **temp SQLite DB + offline reader (`RFID_DISABLED`) + ephemeral HTTP/WS ports**; section 18 swaps in `FakeRfidReader` (injection below) to test real scans without hardware; section 21 swaps in `FakeClock` (injection below) to time-travel the scheduler with zero real-time delays; section 22 injects the **log sink** (`setLogSink`) to verify JSON log formatting and sensitive-data redaction end-to-end; section 23 verifies **persistent authentication sessions** (SHA-256 token hashes in `auth_sessions`, survival across a simulated restart via `reopenDatabase`, concurrent sessions, expiration cleanup, password-change invalidation); section 24 serves the admin-only **server log tail** over `GET /api/logs` — the logger's in-memory ring buffer (`core/logBuffer.ts`) read back post-redaction, with `level`/`limit`/`since` filters, chronological order and non-admins refused); section 25 drives the **recurring-series service** under `FakeClock` (daily/weekly generation, inclusive bounds, rolling horizon, idempotency, DST nonexistent/ambiguous local times, group/delta copying, paused/cancelled rules, edit-from-occurrence, transactional rollback via a temporary RAISE(ABORT) trigger); sections 26–28 cover Phase 3 — the **series HTTP API** (validation, kiosk read-only, calendar with local-date semantics, per-occurrence PATCH, edit-from/pause/resume/cancel, rolling-horizon ticks under `FakeClock`), **roster freezing at start** (atomic snapshot, roster-based reporting, delta-aware scans, legacy fallback for never-frozen sessions, interrupted-start rollback, transition regressions) and **scheduler integration** (boot+tick generation, paused series inert, broken-series isolation, no catch-up) and section 29 the Phase 4 **weekly-calendar UI contracts** (12-week horizon from "today", inclusive week windows, wall-clock 08:30 preserved across a DST transition with shifted UTC instants, per-occurrence PATCH visible in the calendar response, series edit-from-anchor counts, series cancel with explicit `from` — non-retroactive —, kiosk refused on series pause, sessions/reports regressions) and section 30 the Phase 5 **series hardening** (membership provenance: generated rows are `inherited = 1` copies while explicit upserts are 0; `editSeriesFrom` resynchronizes inherited group/participant copies while explicit overrides survive and veto reinsertion; duplicate participants last-wins; PATCH `/sessions/:id` `scheduledAt` 409 `SESSION_OCCURRENCE_MOVE` on occurrences but 200 standalone; frozen roster follows the propagated scope; WS `series:changed` broadcasts created/generated/paused/resumed/cancelled, generation only broadcast when it really materialized rows). `db:verify` uses a fresh DB plus a **copy** of the dev DB. **Neither ever writes `attendance.db`. Extend `api:verify` when adding features.**
- `.env` is loaded only from the **repo root**; the DB path `./attendance.db` is **CWD-relative** (override with `DB_PATH`).

## Architecture

Layers: `api/routers → middleware (auth, validation, error) → services → db/repositories`, and `rfid/reader.ts → scanService → attendanceService → repositories + websocket hub`. Services never touch Express objects; routers never touch SQL or `rfid/`.

- **Boot is idle** (`index.ts`): DB open+migrate → `createApp()` → WS hub → reader monitor → scheduler → wait. **Never STARTS a session** — but the scheduler's boot pass runs one series generation (`runSeriesGeneration` → `generateAllActive`), which may materialize future occurrences as `scheduled` rows (`series.occurrences_generated` log lines) — never starts them. `createApp()` does NOT start the scheduler timer — `api:verify` drives the exported `runSchedulerTick()` directly.
- **Session state machine** (`sessionService`): `scheduled→running→completed`, `scheduled|running→cancelled`, anything else 409. **Mono-lecteur**: at most one `running` (else 409 `SESSION_ANOTHER_RUNNING`). Start works with the reader offline. Start is ONE `db.transaction`: transition + roster snapshot (`sessionRosterRepository.capture` over `sessionRosterRepository.resolveExpectedEntries` — inclusion deltas win, exclusions beat group membership, no groups ⇒ nobody expected) + `freezeRoster` stamping `roster_frozen_at` (skipped when already set; a capture failure rolls back the WHOLE start — session stays `scheduled`, no scan loop). Frozen roster ⇒ later group edits never change the expected participants.
- **Series recurrence** (`seriesService` + pure helpers `services/localTime.ts` — **fully wired: `/api/series` routes + scheduler generation + Phase 5 hardening (membership propagation, WS `series:changed` broadcast on every template change)**): `createSeries` strictly validates the template (real-calendar `YYYY-MM-DD` — SQLite's `date()` **normalizes** e.g. `2026-02-30`→`2026-03-02` so the CHECKs are not the guard; `HH:MM`; IANA tz via `Intl`; weekly ⇒ `weekday` 0–6, daily ⇒ none; `ends_on ≥ starts_on`; ≥1 existing group) and `setSeriesStatus` enforces `cancelled` terminal (else 409 `SERIES_CANCELLED`). `generateOccurrences(seriesId, {horizonWeeks?})` / `generateAllActive` materialize `active` series into `app_sessions` over a rolling horizon (`SERIES_HORIZON_WEEKS`, default 12) anchored on the **injected clock**, "today" being today **in the series timezone**: candidate local dates = pattern matches ∩ [`starts_on`,`ends_on`] ∩ [today, today+horizon] (all inclusive); a date already carrying a row (ANY status — idempotency key `(series_id, occurrence_date)`) is never touched (manual edits, cancellations and frozen history survive). Each new occurrence stores `local_time`/`timezone` beside the UTC `scheduled_at`, **converts the instant per occurrence** so the course keeps its intended wall-clock time across DST (`zonedTimeToUtc` probes zone offsets around the reading: nonexistent spring-forward time → occurrence SKIPPED and reported `nonexistent_local_time`, never shifted; ambiguous fall-back time → deterministic FIRST occurrence), and copies the series' live group scope into `session_groups` + inclusion/exclusion deltas into `session_participants` — as **inherited** rows (migration 009 `inherited = 1`: copies of the series scope, rewritable by a later series edit; manual rows are explicit `inherited = 0`). `editSeriesFrom(seriesId, fromDate, patch)` (whole edit in ONE `db.transaction` — verified by an aborting trigger in `api:verify` §25): rows strictly before `fromDate` and non-`scheduled` rows (running/completed/cancelled) are preserved untouched; eligible future `scheduled` rows matching the edited pattern are rewritten IN PLACE (same id, `session_groups`/`session_participants` kept — see propagation below); non-matching ones are CANCELLED (never deleted); newly required dates (from `max(fromDate, today, starts_on)` within the horizon, `active` series only) are generated like above; the series row is rewritten. **Membership propagation (migration 009)**: rows copied at generation carry `inherited = 1`, so a patch carrying `groupIds` and/or `participants` also resynchronizes those copies on every future `scheduled` occurrence it rewrites; EXPLICIT rows (`inherited = 0` — manual overrides and everything predating migration 009) are never rewritten and even veto the reinsertion of the same (occurrence, student|group). `participants` patches replace the WHOLE series delta list (duplicate studentIds: last wins) and are now editable through `PATCH /api/series/:id`. `cancelSeries(id, {fromDate?})` = `setSeriesStatus(cancelled)` + `cancelFutureOccurrences(from ?? today in the series timezone)` — running/completed/cancelled occurrences and their attendance survive; `listSeries`/`getSeries` are the API read helpers.
- **Scheduler** (`schedulerService`, unref'd 10 s tick, started by `index.ts` only): each tick (and once at boot) first runs `runSeriesGeneration()` — exported wrapper around `seriesService.generateAllActive` in try/catch, systemic failure logged `scheduler.generation_error`, per-series failures isolated inside `generateAllActive` (`series.generation_failed`, warn) — generation only ever creates `scheduled` rows. Then the tick auto-stops the running session once `now ≥ scheduled_at + duration_minutes` (reason `auto_end`), else starts the OLDEST `scheduled` session whose window contains now. A fully **elapsed window never starts** (no catch-up after downtime). Early manual starts are allowed (the auto-stop still applies). The tick's reference time is the **injected clock** (`runSchedulerTick(now = getClock().now())`, default parameter evaluated per call) — see **Clock abstraction + DI**.
- **Auth** (`auth/`, `authService`): scrypt hashes (`scrypt$N$r$p$saltB64$hashB64`, timing-safe), **persistent server-side sessions** + HTTP-only cookie `sid` (`SESSION_TTL_HOURS` default 12, `Secure` only when `COOKIE_SECURE=1`). No JWT. The **same `sid` cookie authenticates the WebSocket handshake** (see **WebSocket**). Roles `admin` > `teacher` > `kiosk`. The `kiosk` account is **read-only server-side** (middleware right after `authRequired`: any non-GET/HEAD on `/api` → 403) and satisfies no `requireRole`. `PATCH /users/:id` changing your OWN role → 409 `SELF_ROLE_CHANGE`; setting a password destroys that user's OTHER sessions (the acting session survives); role changes propagate to live sessions (the user row is reloaded per request). `password_hash` is never returned. **Persistent sessions** (`auth_sessions`, migration 006; repo `db/repositories/authSessions.ts`): the opaque 256-bit token travels ONLY in the cookie and is **never stored** — the row is keyed by `token_hash = SHA-256(token)` (UNIQUE, indexed), with `user_id` (FK CASCADE), `created_at`, `expires_at` (`= now + SESSION_TTL_HOURS`) and `last_seen_at` (throttled touch, ≤ 1 write/session/min). Because it is in SQLite, logins **survive a restart/restore**; expired rows are rejected AND lazily purged on lookup, and swept at boot + each login (`authService.purgeExpiredSessions`). `expireSession`/`sessionCount`/`purgeExpiredSessions` are the test seams (the token expiry honors the injected clock via `isoNow`). The raw token is hashed with `hashToken()` for the WS close comparison (the store only knows hashes).
- **Login rate limiting** (`api/middleware/loginRateLimit.ts`, mounted on `POST /auth/login` before validation): in-memory per process, TWO fixed-window counters — client IP (`LOGIN_FAIL_LIMIT_PER_IP`, default 10) and case/space-normalized username (`LOGIN_FAIL_LIMIT_PER_USER`, default 5) within `LOGIN_RATE_WINDOW_MINUTES` (15). ANY non-2xx login response counts as a failure (401 bad credentials AND 400 malformed body — a locked-out caller gets 429 whatever it sends); a successful login clears both buckets. Over the threshold the bucket locks with progressive backoff `LOGIN_BACKOFF_BASE_SECONDS` (30) × 2^(failures − limit), capped at `LOGIN_BACKOFF_MAX_MINUTES` (15). Locked out → 429 `RATE_LIMITED` + `Retry-After` (seconds), identical code/message whatever dimension tripped or whether the account exists (anti-enumeration); the username counter stops distributed attacks on one account while the IP counter stops username spraying. `req.ip` honors `X-Forwarded-For` ONLY when `TRUST_PROXY=1` (default off — forged headers cannot evade the limit otherwise). Map is bounded (10 000 keys, expired-first eviction, fail-open). Exported test hooks `resetLoginRateLimits()` / `shiftLoginRateLimitClock(ms)` drive `api:verify` section 17.
- **Scan pipeline** (`attendanceService.handleScan(uid)`): EVERY scan is journaled in `card_scans` (`accepted|duplicate|unknown|expired|out_of_group|manual`); attendance state (`app_attendances`) is written only on the first ACCEPTED scan per (session, student). Expected scope = `sessionRepository.isExpectedParticipant` (inclusion delta wins, exclusion beats group membership, else membership; no-group sessions accept everyone — legacy behavior). An unexpected student → `out_of_group`, journaled but never counted present. Broadcasts `attendance:scanned` (content **camelCase**, DB rows snake_case). Scan loop = async generation-guarded loop, started/stopped by session transitions.
- **Manual presence mark** (`attendanceService.markPresentManually(sessionId, studentId)` ← `POST /api/sessions/:id/attendance/manual` body `{studentId}`): teacher correction during a `running` session (409 `SESSION_NOT_RUNNING` otherwise, 409 `ALREADY_PRESENT` if already present, 404 unknown student). Poses the attendance state AND journals a `manual` `card_scans` event (uid/card_id NULL); the session's group scope is deliberately NOT enforced (explicit override). Broadcasts `attendance:scanned` with `result:"manual"`, `uid:""`.
- **WebSocket** (`websocket/hub.ts` protocol + module-singleton `broadcastEvent`; `server.ts` transport): two transports share one hub (standalone `WS_PORT`, and the `/ws` upgrade on the HTTP server — what the client uses). Connect → `status` snapshot (reader + active session); `{"cmd":"get_status"}` re-requests. Events: `reader:status`, `session:started|stopped|updated`, `attendance:scanned`, `attendance:reset`, `series:changed` (`{action: created|edited|paused|resumed|cancelled|generated, series_id, occurrences?}` — broadcast by every `seriesService` template change and by generation ONLY when it actually materialized rows). **WS auth = the same `sid` cookie as HTTP, resolved at the handshake** (ws `verifyClient` on BOTH transports via the shared `createTransportServer`, `authService.resolveToken` — no JWT, no protocol change; the browser sends the cookie automatically on the same-origin handshake): absent/invalid/expired → HTTP 401, the upgrade never completes. A connection whose session is destroyed while open (logout, password reset — `sessionStore.onSessionDestroyed` hook, which notifies with the token HASH since raw tokens are never persisted; the transport compares `hashToken(clientToken)`) or whose TTL expires (unref'd 60 s sweep `revalidateConnectedClients`, exported for `api:verify`) is closed with code **1008** — HTTP and WS therefore react identically to a invalidated session.
- **`RfidReader` abstraction + DI** (`rfid/reader.ts`): the interface — `isOnline()`, `readCard(): Promise<{decID, hexID}>`, `beep()` — is the ONLY contract the app sees; nothing outside `rfid/reader.ts` touches `rfidApi.js`. `scanService` and `readerService` resolve the **active reader** via `getReader()` on every operation (the scan loop re-resolves per iteration → a swap is honored while running); never the hardware singleton. `setReader(reader)` replaces the active reader and returns a restore function. Production default unchanged: the hardware adapter (lazy `require("../../../rfid/rfidApi.js")` — USB worker starts only on first use) or, when `RFID_DISABLED=1`, the offline stub (never online, reads that never resolve, `beep()` rejects). **`FakeRfidReader`** (`rfid/fakeReader.ts`): `setOnline(bool)` (going offline rejects the armed reads, like losing the USB link), `presentCard(uid, hexID?)` feeds the next `readCard()` (buffered if none armed yet), `pendingReads`/`beepCount` getters for deterministic test sync. `api:verify` section 18 injects it: scans processed by the real loop, hot offline/online transitions, `READER_BUSY`, `READER_TIMEOUT` (service-level `nextCard(150)`), 503 paths — then restores the default reader.
- **Clock abstraction + DI** (`core/clock.ts`): typed `Clock` interface (`now(): Date`); production default `systemClock` (system clock — boot and unrelated code unchanged), resolved through `getClock()` at each use; `setClock(clock)` replaces the active clock and returns a restore function — same pattern as the reader. Every timestamp the app writes follows it: `isoNow()` (`db/types.ts`) resolves the active clock per call, so `sessionService` transition stamps (`started_at`/`ended_at`/`updated_at` via `sessionRepository`), scan/journal timestamps and the default `scheduledAt` of `POST /api/sessions` all land on the injected clock. `schedulerService.runSchedulerTick(now = getClock().now())` is timed by it. **`FakeClock`** (`core/fakeClock.ts`): `set(ISO|Date)` / `advance(ms)`, defensive `now()` copy. `api:verify` section 21 injects it and drives `runSchedulerTick()` — scheduled start on the exact inclusive lower bound, auto-stop on the exact end, no catch-up after a time jump, exclusive upper bound, oldest-window-first under mono-lecteur, deterministic `started_at`/`ended_at` — never starting the production timer. Auth-session `expires_at`/`last_seen_at` follow it too (they are `isoNow()` values). Deliberate exceptions keeping their own real-time test hooks: `loginRateLimit` and the **logger timestamps** (see **Structured logging**).
- **Structured logging** (`core/logger.ts`): the ONLY runtime log exit — no `console.*` in server code (dev CLIs `db:verify`/`api:verify`/seed keep their own console output). One JSON line per event: `{ timestamp, level, component, event, ...context }`; English dotted `event` ids (`auth.login_failed`, `scan.accepted`, `http.error`, `scheduler.started`…), typed context fields, never French prose. `LOG_LEVEL` env (debug|info|warn|error, default info, read live); default sink = stdout (debug/info) + stderr (warn/error); **`setLogSink(sink)`** test seam (same DI pattern as reader/clock — `api:verify` section 22 captures lines with it). Module loggers: `logger.child({ component: "…" })`. **Redaction is enforced at emit**: keys `password`/`password_hash`/`token`/`sid`/`cookie`/`authorization`/`secret`… → `"[redacted]"` (recursive, case/underscore-insensitive), `uid`/`decid`/`hexid` → masked to the last 4 digits (`maskUid`), no student names in scan logs (IDs only). **Stack traces are logged ONLY for internal 500s** (HTTP error middleware, scheduler tick crash) — decided by the caller via `errorFields(err, { stack: true })`; 4xx lines carry method/path/status/code only. Logs never change API responses: SQL/internal details still never leave the server. Timestamps use the REAL clock (deliberate exception to the injected `Clock`). Every emitted line is ALSO mirrored (post-redaction) into a bounded in-memory ring buffer (`core/logBuffer.ts`, `LOG_BUFFER_SIZE`, default 500) — the admin-only `GET /api/logs` tail; the buffer is a second destination beside the sink, so `setLogSink` never starves it (runtime dep is one-way: `logger → logBuffer → config/env`, `logBuffer` never imports the logger).
- **Reader** (`POST /api/reader/next-card`): one-shot card read for association dialogs — 409 `READER_BUSY` while a session loop holds the reader, 503 `READER_OFFLINE`, 504 `READER_TIMEOUT` after 45 s. `POST /reader/beep` (503 offline).

## Database (`server/src/db`)

- SQLite / better-sqlite3, WAL, `foreign_keys=ON` per connection; versioned by `PRAGMA user_version` (**currently 9**) in `db/migrations.ts` (transactional, all-or-nothing, refuses partially-legacy DBs).
- Tables: `users`, `groups`, `app_students`, `cards` (uid TEXT UNIQUE **decimal string** = exactly what `decID` produces; at most one ACTIVE card per student via partial unique index; `revoked_at` NULL = active), `app_sessions` (`created_by` = FK users ON DELETE SET NULL — who created the session, NULL = unknown; HTTP/WS expose the joined `created_by_username`), `session_groups` (session↔group M:N — the roster is the live UNION of the session's groups), `app_attendances` (STATE, UNIQUE(session_id, student_id)), `card_scans` (history, duplicates included), `auth_sessions` (login sessions: `token_hash` UNIQUE = SHA-256 of the cookie token — raw token never stored — `user_id` FK CASCADE, `created_at`/`expires_at`/`last_seen_at`).
- **Recurring-session schema (migration 008; the schema is paired with `services/seriesService` — generation + edit-from-occurrence — fully wired since Phase 3: `/api/series` routes + scheduler generation + roster freezing at start)**: `session_series` = recurrence template (label, `recurrence` daily|weekly + `weekday` 0=Sunday…6=Saturday JS-`getDay` convention — required when weekly, `local_time` 'HH:MM' + IANA `timezone` (DEFAULT `'UTC'`), `duration_minutes`, inclusive local-date range `starts_on`/`ends_on`, `status` active|paused|cancelled, `created_by` FK SET NULL) · `session_series_groups` (series↔group M:N, mirror of `session_groups`) · `session_series_participants` (series-level inclusion/exclusion deltas, PK (series_id, student_id), `included` 0/1 CHECK) · `session_participants` (the same deltas per occurrence). **Migration 009** adds the `inherited` flag (`inherited INTEGER NOT NULL DEFAULT 0 CHECK (inherited IN (0,1))`) to `session_groups` AND `session_participants` — purely additive ALTER, every pre-existing row 0 (explicit): 1 marks a generation-written copy of the series scope that a series edit may rewrite. `app_sessions` occurrence columns: `series_id` (FK ON DELETE SET NULL — deleting a series never destroys generated attendance history), `occurrence_date` (local `YYYY-MM-DD` identity of an occurrence; partial UNIQUE index `ux_app_sessions_series_occurrence` on (series_id, occurrence_date) WHERE series_id IS NOT NULL = generation idempotency key), `local_time`, `timezone` (NOT NULL DEFAULT `'UTC'` — truthful for pre-008 rows), `roster_frozen_at` (roster snapshot taken). `session_roster` = the participant snapshot frozen at session start (denormalized `full_name`/`group_name` so renames/deletions never rewrite history, UNIQUE(session_id, student_id)): **immutable** — BEFORE UPDATE/DELETE triggers RAISE(ABORT) on any explicit write; because SQLite fires row triggers for FK actions, the WHEN clauses exempt exactly the SET-NULL-student_id (student deleted, row kept) and CASCADE-rows (session deleted) shapes. Repositories `sessionSeriesRepository` / `sessionParticipantRepository` / `sessionRosterRepository` (`capture` = one-shot transactional snapshot; reads only afterwards); `sessionRepository.freezeRoster(id, at)` stamps `app_sessions.roster_frozen_at`. Existing sessions stayed standalone (`series_id`/`occurrence_date`/`local_time` NULL, `roster_frozen_at` NULL, `timezone` 'UTC'); the compat views/triggers are untouched (explicit column lists hide the new columns from the legacy side).
- **`students` / `sessions` / `attendances` are compatibility VIEWS** (INSTEAD OF triggers over `app_*`) and `legacy_*` tables archive pre-migration rows. The server reads/writes `app_*` only; the views exist solely for ad-hoc/external SQL. **Never `CREATE INDEX` / `CREATE TABLE IF NOT EXISTS` / `RETURNING` against the views** (use `lastInsertRowid`). Dropping views + `legacy_*` is deferred cleanup.
- Timestamps: TEXT ISO-8601 **UTC** with ms + `Z` (`isoNow()`, which follows the injected clock — `core/clock.ts`); schema DEFAULTs (`strftime`) truncate to whole seconds — verify code tolerates ±1 s drift.
- UIDs are decimal **strings** end-to-end: `WHERE uid = 1234` (JS number) never matches — bind strings / `normalizeUid()`.
- Repositories are factories; singletons exported by `db/index.ts` (importing it also migrates). Only `services/` and the seed/verify CLIs may use repositories.

## API conventions (`server/src/api`)

- Envelopes via `api/http.ts` helpers: `{data}` | `{data, meta:{total}}` | `{error:{code,message}}`; `asyncHandler` replaces per-route try/catch. Only `INTERNAL` logs a stack; SQL details never leak.
- Public: `GET /api/health`, `/api/auth/*` (login → `sid` cookie, logout, me). Everything else behind `authRequired`; `/api/users`, `/api/backups` and `/api/logs` admin-only.
- **Server logs** (`GET /api/logs`, **admin-only**, `services/logService` over `core/logBuffer`): read-only view of the logger's bounded in-memory ring buffer (`LOG_BUFFER_SIZE`, default 500 lines — volatile, never persisted, distinct from the `card_scans` audit journal). `logger.emit` mirrors every emitted line into the buffer via `captureLog` (a second destination alongside the sink, so `setLogSink` injection in `api:verify` doesn't starve the tail). Entries are the **already-redacted** records (`fields` = context minus reserved keys, plus the raw `line`) — the route is admin-only because a raw line can still carry a stack trace for internal 500s. Query `level` (exact, `qEnum`) / `limit` (`qInt`, cap 5000) / `since` (only `seq >` since — incremental tail); returns **oldest → newest** with `meta.capacity`/`buffered`. No write/clear endpoint (pure read; the client only resets its own view).
- Error codes: 401 `NOT_AUTHENTICATED`/`INVALID_CREDENTIALS`, 403 `FORBIDDEN`, 400 `VALIDATION_ERROR`/`INVALID_JSON`/`INVALID_REFERENCE`, 404 `NOT_FOUND`, 409 `GROUP_NAME_TAKEN`/`USERNAME_TAKEN`/`UID_ALREADY_REGISTERED`/`STUDENT_NUMBER_TAKEN`/`CARD_ALREADY_ASSIGNED`/`CARD_ALREADY_REVOKED`/`SESSION_NOT_RUNNING`/`SESSION_ALREADY_RUNNING`/`SESSION_ANOTHER_RUNNING`/`SESSION_INVALID_TRANSITION`/`SESSION_OCCURRENCE_MOVE`/`READER_BUSY`/`SELF_ROLE_CHANGE`/`ALREADY_PRESENT`/`RESTORE_SESSION_RUNNING`/`SERIES_CANCELLED`, 413 `PAYLOAD_TOO_LARGE`, 429 `RATE_LIMITED` (+ `Retry-After`), 500 `BACKUP_FAILED`, 503 `READER_OFFLINE`, 504 `READER_TIMEOUT`.
- Hand-rolled typed validators (`api/validate.ts`): `vString/vInt/vIntArray/vIsoDate/vEmail/vUid/vUsername/vPassword/vRole`, `rejectUnknownFields` (unknown body field → 400), query helpers `qInt/qDate/qEnum` (empty query value = absent; `qDate` strict `YYYY-MM-DD`).
- **Sessions**: `POST /api/sessions` takes `groupIds` (array, **at least one required** — the implicit "all students" was dropped) or legacy single `groupId`; sending both → 400. Every session returned by HTTP/WS carries `group_ids` (sorted); `app_sessions.group_id` is a non-authoritative legacy mirror the server never reads. **`PATCH /api/sessions/:id`** edits `label`/`scheduledAt`/`durationMinutes` on `scheduled` rows only (else 409 `SESSION_INVALID_TRANSITION`; a **series occurrence** additionally refuses `scheduledAt` → 409 `SESSION_OCCURRENCE_MOVE` — its instant follows the series' local slot, the identity + idempotency key; moves go through `PATCH /api/series/:id`). **`GET /api/sessions/calendar?from&to`** (both required `qDate`, inclusive): occurrences keyed on their CALENDAR DAY — series occurrences match their **local** `occurrence_date` (series timezone), standalone sessions their UTC day (`substr(scheduled_at,1,10)`); rows carry `series_id`/`series_label`/`series_status`/`series_recurrence`, `group_ids`, `group_name` (first group or NULL) and `participant_count` (frozen-roster count once started, else live expected count: inclusion > exclusion > membership, no groups ⇒ 0).
- **Series** (`/api/series`, `seriesService`; any authenticated role, kiosk GET allowed and refused 403 by the read-only middleware on POST/PATCH): `GET /` = `listSeries` (rows + `group_ids` arrays), `POST /` = `createSeries` (201, returns the `getSeries` detail; `vLocalDate`/`vLocalTime` validators, `participants:[{studentId,included}]`), `GET /:id` = detail with participants, `PATCH /:id` = `editSeriesFrom` (required `fromDate` that must be an EXISTING occurrence date, else 404; unknown/incomplete fields 400; `participants:[{studentId,included}]` editable since Phase 5 — replaces the whole series delta list and resynchronizes the INHERITED membership copies of future scheduled occurrences, explicit per-occurrence overrides survive), `POST /:id/pause` / `/:id/resume` / `/:id/cancel` (cancel → `{series, cancelled:[sessionIds]}` via `cancelSeries`; second cancel or resume-after-cancel → 409 `SERIES_CANCELLED`; edits on a cancelled series → 409). NO DELETE endpoint (series rows survive; FK `ON DELETE SET NULL` would detach occurrences anyway).
- **Reporting** (`/api/reports/*`, read-only `reportingService`, any authenticated role): `GET /sessions` (filters `from|to|groupId|status` → rows + `present_count`/`scan_count`; `groupId` matches via `session_groups`), `GET /sessions/:id` (full roster + `summary:{present,absent,total}`; branches on `roster_frozen_at`: frozen sessions are reported from the immutable `session_roster` snapshot — attendees outside the roster (manual marks) added as present — never-frozen sessions keep the legacy live-union query; the CSV export follows the same branch), `GET /sessions/:id/export` → raw CSV **file response** (not the JSON envelope): UTF-8 **BOM** for Excel, timestamps raw ISO-UTC on purpose. Date filters are **UTC calendar dates** (`substr(scheduled_at,1,10)`) — sessions near midnight land on the adjacent day.
- **Student CSV import** (`POST /api/students/import`, raw `text/csv`, 2 Mo max → 413): header `prénom, nom, groupe, email, id` (accents/case/BOM/`;` tolerated); only first+last name required; `id` = RFID card UID to assign (card created if unknown; row refused if held by another active student); unknown group names created; invalid rows skipped and reported `{line, message}`; valid rows inserted in ONE transaction; returns `{imported, skipped, groups_created, errors}`.
- **Database backups** (`/api/backups`, **admin-only**, `services/backupService`): `POST /api/backups` creates a consistent snapshot of the live DB via better-sqlite3's `db.backup()` (SQLite Online Backup API — WAL included, the live file is **never copied directly**) into `BACKUP_DIR` (default `./backups`, CWD-relative, created on demand), stored as `attendance-YYYYMMDD-HHMMSS[-N].db` (UTC stamp, collision suffix), returns `{filename, size_bytes, created_at}` — never a path. `GET /api/backups` lists them (newest first); `GET /api/backups/:filename` downloads the raw `.db` (**file response**, `application/octet-stream` + attachment, errors keep the `{error}` envelope). Filename validated by strict whitelist regex (anything else → 400, traversal-proof); unknown file → 404; creation/read failure → 500 `BACKUP_FAILED` (SQLite error logged server-side only). No delete endpoint (deferred).
- **Database restore** (`POST /api/backups/restore`, **admin-only**, `backupService.restoreBackup`): raw `application/octet-stream` body (max `BACKUP_RESTORE_MAX_MB`, default 100 → 413), replaces the ENTIRE live database with the uploaded `.db`. Precaution order: uploaded bytes staged in a temp file **next to the live DB** (same volume → atomic rename) → validated (magic header, `PRAGMA integrity_check` must be `ok`, `user_version` ≤ target with migrations applied to the staged copy, all core `app_*`/`users`… tables present) → refused **400 `VALIDATION_ERROR`** on any failure (live DB never touched) → running session → 409 `RESTORE_SESSION_RUNNING` (double-checked just before closing, re-check 409 removes the superfluous safety backup) → safety backup of the CURRENT DB created first (same naming, stays listed/downloadable; its failure aborts the restore) → **strictly synchronous swap** (no awaits: close connection, remove `-wal`/`-shm`, rename live→old, rename staged→live, `reopenDatabase()`), rollback restores the old file and reopens on any failure. `db/index.ts` exports `db` + the repositories as mutable `let` (CJS live bindings) rebound by `reopenDatabase()` — every service references them at call time, so the swap is transparent app-wide without a restart; `getCurrentDbPath()` (db/database.ts) tracks the opened path. Success → `{restored_size_bytes, safety_backup}`.

## Frontend (`client/`)

Plain hand-rolled CSS in `src/styles.css` (BEM-ish classes, CSS variables) — no UI library. All user-facing strings French; server comments French, client comments mostly English — follow the file you edit.

- Layering: `pages/ → components/ → hooks/ (providers) → api/ → types/`. Pages never call `fetch` — one `api/<resource>.ts` module through `api/client.ts` (envelope unwrap, `credentials:"same-origin"`, `ApiError`, 401 → login handler, `toUiMessage()` → French errors, `downloadFile()` for exports, `postRaw()` for the CSV import and the `.db` restore upload — body `string | Blob`).
- WS: one `LiveSocket` per tab (`websocket/client.ts`, URL from `location`, exponential-backoff reconnect, `get_status` on reopen). `WsProvider` holds `connection`/`readerOnline`/`activeSession`, a **`serverEpoch` counter** bumped by `session:*`/`status` (pages reload their lists on epoch change) and `subscribe(event, handler)` for `attendance:scanned`. The handshake rides on the login cookie (server-side WS auth) — `LiveSocket` sends nothing special and only lives inside `RequireAuth`, so no frontend change was needed for WS authentication.
- Routing: `RequireAuth` guards the shell; `RequireAdmin` gates `/users`, `/database` and `/logs` (admin « Base de données » page: “Créer une sauvegarde” button + per-backup “Télécharger” via `downloadFile()`; admin « Journaux » page (`LogsPage` → `api/logs.ts`): auto-refreshing redacted log tail with level filter + client-side search, newest first); `RequireNotKiosk` redirects kiosk accounts to `/kiosk` (rendered **outside AppLayout**, own `WsProvider`). `LoginPage.homeFor(role)` sends kiosk to `/kiosk`. `/reports` `<Navigate>`s to `/sessions` (reporting merged there; selected session kept in the `?session=` search param). Unknown route → `/`.
- **Kiosk is a pure projection of backend state**: never starts/stops sessions nor touches the device from `/kiosk`; exiting the page never stops the session. `hooks/useKioskState.ts` merges the WS snapshot + live events + authoritative HTTP resyncs into one `phase`; scan feedback is transient (4.5 s auto-dismiss, deduped by `sessionId|uid|result|scannedAt`; `accepted` AND `manual` increment the counter — `manual` shows no student-facing overlay nor sound, deltas corrected on resync). "Session terminée" reverts to idle after 2 min.
- **Roster gotcha**: `GET /sessions/:id/attendance` returns ONLY students who scanned — the expected roster is built client-side from `GET /students` filtered by `session.group_ids` (server-side equivalent: `attendanceRepository.getSessionReport`).
- Table sorting everywhere: `lib/sort.ts` (`sortRows`, French collation, nulls last, stable) + `hooks/useSort.ts` (click cycle asc → desc → default) + `components/common/SortHeader.tsx`. Notifications via `hooks/useToast.tsx`.
- **Sessions page = two tabs** (Phase 4), same `/sessions` route: weekly **Calendrier** (default) and **Historique et rapports** (the former page verbatim — filters, counters, `?session=` report, CSV export). Active tab lives in `?vue=historique`. No new routes. `components/sessions/SessionsCalendar.tsx` owns the tab: week state (Monday-anchored), `GET /sessions/calendar?from&to` via `api/sessions.ts#getCalendar` (inclusive LOCAL dates — series occurrences match their `occurrence_date`, standalone their UTC day), reload on `serverEpoch` and on WS `session:started|stopped|updated` or `series:changed` (debounced; `attendance:scanned` must NOT reload the grid). `WeekCalendar.tsx` renders a time grid (configurable visible hours, persisted in localStorage `rfweb.calendar.range`) with prev/next/Today nav; series occurrences are placed at `occurrence_date` + `local_time` (wall-clock, DST-proof), standalone at `scheduled_at` in browser TZ; overlapping blocks share the column width (`lib/calendar.ts#layoutDay`), never hidden; blocks outside the hour range clip at the edges.
- **Session planning workflows** (`components/sessions/`): `CreateSessionDialog` (segmented Ponctuelle via the preserved `SessionForm` / Récurrente via `SeriesForm`) → `POST /sessions` or `POST /series` (participants deltas: accepted on series creation AND series edit — `PATCH /series/:id` replaces the whole delta list; still rejected on standalone sessions). `StudentPicker` = searchable include/exclude deltas over real `GET /students`+`GET /groups`, deduped via `Map<studentId, included>`, group-membership vs individual delta visually separated. `SessionDetailsDialog` (click a block) = read-only for completed/cancelled, running links to the attendance page, scheduled offers Modifier/Annuler, plus per-series pause/resume and series cancel `from` the clicked occurrence. `SessionEditDialog` offers the explicit scope for occurrences: « Uniquement cette occurrence » (`PATCH /sessions/:id` — label/durée only: the form hides the datetime field for occurrences, which cannot move since Phase 5) vs « Cette occurrence et les suivantes » (`PATCH /series/:id` with `fromDate = occurrence_date`, participants deltas included — `SeriesForm` exposes the `StudentPicker` in edit mode too); every 409 (`SESSION_INVALID_TRANSITION`, `SERIES_CANCELLED` — occurrence started / series revised meanwhile) toasts the French server message AND triggers a calendar resync. `SessionPage` adds « Modifier » (scheduled only) + a « ↻ Série récurrente » chip.
- **Series changes broadcast `series:changed`** (Phase 5): `SessionsCalendar` subscribes (debounced reload), so local AND remote creates/edits/pause/resume/cancel/horizon generation keep the grid current. After a local creation a single ≈12 s fallback timer also resyncs (the scheduler's rolling materialization may land after the initial « generated » event). Weekly series = a SINGLE weekday (server pattern) — the form exposes one weekday select, never a day list.

## Gotchas

- `attendance.db` (+ `-wal`/`-shm`) is **live state — never delete or reset it**. A `running` session at boot is pre-existing data: the scheduler auto-stops it within ~10 s if its window elapsed, otherwise `POST /api/sessions/:id/stop`; until then `start` on any other session 409s.
- **A `scheduled` session left in the DB WILL auto-start itself** on a running server once its window contains now — cancel it to keep the server idle (`api:verify` never starts the timer).
- **Port 8080 conflict**: the standalone WS transport may clash with local tooling (e.g. llama.cpp — on Windows both can "bind" simultaneously and hijack each other's connections). The client and dev proxy never use it; a failed standalone bind is a non-fatal boot error. Set `WS_PORT` only for external tools.
- tsconfig `rootDir: server/src` ↔ `outDir: dist/server` are at EQUAL depth so the adapter's `../../../rfid/rfidApi.js` require path resolves identically under `tsx` and in `dist/` — don't change one without the other.
- Never hardcode mutable dev-DB values (group names…) in `db:verify` assertions — compare against current physical tables.
- `api:verify`/`db:verify` never write `attendance.db` (temp dirs; DB handle closed in `finally` for Windows locks).
- Without the USB reader the server just logs the JSON line `scan.reader_offline` (warn) once per scan-loop start; sessions still start/stop. `RFID_DISABLED=1` silences USB entirely.

## Verify with

`npm run typecheck` · `npm run db:verify` · `npm run api:verify` · `npm run build` · `npm start` — boot must print ONLY the structured JSON lines `db.schema_up_to_date` (version 9), `http.listening`, `ws.listening`, `scheduler.started` (+ `rfid.*` lines, e.g. `rfid.disabled` when `RFID_DISABLED=1`, + `series.occurrences_generated` when active series materialize future `scheduled` rows) — **no session is ever STARTED at boot**. Then `GET /api/health` → `{"status":"ok"}` and `POST /api/auth/login` (admin after `npm run db:seed`) → 200 + `sid` cookie. Manual reporting/import flows: use a throwaway `DB_PATH` + seed, never `attendance.db`.

## Deferred (do not assume they exist)

No global rate limiting (only `POST /api/auth/login` is rate-limited — see **Auth**), no HTTPS (enable `COOKIE_SECURE` only behind TLS), no test/lint frameworks beyond `db:verify`/`api:verify`, no Fastify. No user deletion/deactivation field (remove access = password reset or role change). Report pagination/PDF/filtered-range export deferred (per-session export only). Compat views + `legacy_*` drop deferred. Recurring sessions: the schema (migration 008 — `session_series` & co.), the domain service (`seriesService` generation + `editSeriesFrom` + `cancelSeries`), the `/api/series` routes, scheduler generation and roster freezing at start are ALL live (see **Series recurrence**). Still deferred: a DELETE endpoint for series, a per-occurrence membership-override UI (the repositories support explicit `inherited = 0` upserts — nothing exposes them via HTTP yet) and session-group edits after creation (`groupIds` fixed at creation for standalone sessions; `PATCH /sessions/:id` covers only `label`/`durationMinutes` on occurrences — `scheduledAt` moves are refused by design, `SESSION_OCCURRENCE_MOVE` — and label/duration on standalone sessions; the live roster of a never-frozen session still follows group-MEMBERSHIP changes because it is derived).
